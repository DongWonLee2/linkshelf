# ADR-0003: 테스트 전략

- 상태: Accepted
- 작성일 / 사람 승인일: 2026-10-14 / 2026-10-14
- 결정 책임자: 저장소 소유자
- 관련 Spec/R-ID: PRD-01 (링크 저장)
- 사용한 외부 근거: 없음

## 맥락

TDD로 구현하고, 테스트 이름으로 R-ID를 추적한다. 어떤 테스트를 어느 경계에서 쓸지 정하지 않으면 모든 것을 `@SpringBootTest`로 쓰거나 반대로 목(mock)만 쓰게 된다.

## 평가 기준

1. 요구사항(HTTP 상태 코드·오류 형식)을 실제로 검증 2. 실행 시간 3. 실패 원인 파악 쉬움

## 대안

| 대안 | 장점 | 단점·위험 | 근거·실험 |
|---|---|---|---|
| A. 단위 + 웹 슬라이스(`@WebMvcTest`) + JPA 슬라이스(`@DataJpaTest`) + 소수 통합(`@SpringBootTest`) | 경계별로 빠르고 원인이 분명 | 슬라이스 설정 관리 필요 | — |
| B. 통합 테스트 위주(`@SpringBootTest` + H2) | 실제 동작에 가까움, 설정 단순 | 느려짐, 실패 원인이 넓음 | — |
| C. 단위 테스트 위주(목 사용) | 매우 빠름 | DB 유일 제약·HTTP 계약을 검증 못 함 | — |

## Agent의 추천과 근거

A를 추천한다.
- 단위: URL 정규화 같은 순수 로직
- 웹 슬라이스: 요청 검증, 상태 코드(201/400/409), `ProblemDetail` 형식
- JPA 슬라이스: 중복 URL 유일 제약
- 통합: 기능당 1~2개, 저장 → 응답 전체 흐름
- 테스트 이름: `R_LINK_01_...` 처럼 R-ID로 시작하거나 `@DisplayName("R-LINK-01: ...")`
- 검증기 검증: 기능마다 기대값을 일부러 틀리게 바꿔 FAIL 확인(커밋하지 않음)

## 사람의 최종 결정과 실제 판단 이유

Agent 추천안 채택. 판단 이유: 사용자 위임

## 포기하는 것·운영 영향

- 트레이드오프: E2E·성능·동시성 테스트는 MVP-1에서 하지 않는다(동시에 같은 URL 저장은 DB 유일 제약에 맡김).
- 되돌리기: 쉬움.

## 결정 검증

- 실행할 실험: 5단계 오류 주입
- 성공 판정: 주입 시 FAIL, 원복 시 PASS
- 재검토 트리거: 테스트 실행 시간이 1분 초과, 같은 버그가 테스트를 통과해 재발
