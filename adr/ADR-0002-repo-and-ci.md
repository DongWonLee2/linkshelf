# ADR-0002: 저장소 구조와 CI

- 상태: Accepted
- 작성일 / 사람 승인일: 2026-10-14 / 2026-10-14
- 결정 책임자: 저장소 소유자
- 관련 Spec/R-ID: 전체
- 사용한 외부 근거: 런북 결정표(GitHub만 사용, public 저장소)

## 맥락

백엔드를 먼저 만들고 MVP-3에서 프론트엔드를 붙인다. PR마다 테스트가 자동으로 돌고, 테스트를 통과하지 못한 변경이 `main`에 들어가지 않아야 한다.

## 평가 기준

1. 한 PR에서 백엔드·프론트·문서를 함께 추적 2. 무료 3. 설정이 적음 4. 에이전트가 보호 규칙을 우회할 수 없음

## 대안

| 대안 | 장점 | 단점·위험 | 근거·실험 |
|---|---|---|---|
| A. 모노레포(`backend/`, 이후 `frontend/`) + GitHub Actions | spec·문서·코드가 한 저장소, 한 PR로 추적, public은 Actions 무료 | 경로별 CI 분리가 필요해짐(프론트 추가 시) | — |
| B. 백엔드·프론트 저장소 분리 | CI·권한 독립 | Issue·spec이 두 곳으로 갈림, 1인 프로젝트에 과함 | — |
| C. 모노레포 + 외부 CI | — | 도구 추가, 런북 범위 밖 | — |

## Agent의 추천과 근거

A를 추천한다.
- CI: `.github/workflows/ci.yml`, `pull_request`와 `main` push에서 JDK 21 설정 → `cd backend && ./gradlew test`. 실패하면 종료 코드로 잡이 실패한다.
- `main` 보호: PR 필수, CI 잡 통과 필수, force push·삭제 금지(브랜치 보호 또는 ruleset, 4단계에서 승인 후 설정).
- 브랜치 이름: `feat/<issue>-<slug>`, `fix/<issue>-<slug>`, `chore/<slug>`, 임시 검증은 `tmp/<slug>`.
- 병합은 사람이 한다.

## 사람의 최종 결정과 실제 판단 이유

Agent 추천안 채택. 판단 이유: 사용자 위임

## 포기하는 것·운영 영향

- 트레이드오프: 1인 저장소에 PR 필수 규칙을 걸면 작은 수정도 PR을 거쳐야 한다. 관리자 우회 허용 여부는 4단계에서 정한다.
- 되돌리기: 보호 규칙은 언제든 해제 가능하다.

## 결정 검증

- 실행할 실험: `tmp/ci-should-fail`에 실패 테스트를 넣어 CI FAIL 확인, 보호 규칙 재조회
- 성공 판정: 실패 CI 링크 1개, 성공 CI 링크 1개, 보호 규칙 조회 결과
- 재검토 트리거: 프론트엔드 추가(MVP-3) 시 경로별 잡 분리
- 재검토 기록(2026-10-15, spec 003 plan, advisor 판단): 경로별 분리는 **보류**. 경로 필터로 건너뛴 필수 검사는 Pending으로 남아 병합이 막히고, 프론트 E2E는 백엔드를 띄우므로 백엔드 변경에도 돌아야 한다. `frontend-e2e` job은 모든 PR에서 돈다([spec 003 research R4](../specs/003-first-screen/research.md)).
